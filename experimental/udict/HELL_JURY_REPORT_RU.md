# HELL JURY — PZ03 UDICT v0.2: инженерный разбор

Дата: 2026-10-21. Платформа теста: Linux, Python 3.13.5; Zstandard CLI установлен. **Это ограниченный лабораторный аудит, а не сертификация безопасности.**

## Исправленные проблемы

| № | Проблема | Доказательство | Статус |
|---|---|---|---|
| 1 | Данные `0xFF` конфликтуют с префиксом токена | специальные тесты двоичных строк с `0xFF` | исправлено: `FF 00` — буквальный FF, `FF 01..40` — токены |
| 2 | Жадный поиск максимальной фразы может проиграть паре коротких | `abcde/abc/defgh`, вход `abcdefgh`: 5 Б против 4 Б | исправлено: DP для коротких блоков и режимы CPU-бюджета |
| 3 | Тренировка шумного словаря расходовала много памяти | 256 КиБ шума: ~46 МиБ пиковых отслеживаемых Python-выделений, ~2 с | ранний выход по энтропии, ограничение кандидатов; повторный шумовой тест ~0,03 МиБ и ~0,001 с |
| 4 | Проверка SHA256 только **декодированных** данных могла принять изменённый контейнер | первый fuzz: 16 успешных верификаций среди 12 000 модифицированных архивов | добавлена вторая SHA-256 по сериализованным байтам; тот же тест: 12 000 отказов / 12 000 |
| 5 | Нулевые блоки занимали слишком много после DEFLATE | 1 МиБ нулей из восьми блоков | режим FILL: примерно 262 Б полного контейнера |
| 6 | Повторы между файлами не использовались | два одинаковых бинарных файла | добавлена exact-hash reference с байтовой проверкой и окном 64 блока |
| 7 | При малых вариантах между файлами DEFLATE не переиспользовал историю | 16 близких версий кода | ZDICT с последним 32-КиБ восстановленных байтов |
| 8 | В тестовой программе отсутствовал `import zlib` | первые тесты завершались NameError | исправлено; падения тестового кода не засчитывались за ошибки архиватора |

Ни одна такая находка сама по себе не доказывает нарушение сохранности файлов в исходной ALFA: это ошибки/слабости **нового экспериментального модуля**, найденные в ходе разработки.

## Итог тестов

- Новые unittest: **24/24 групп PASS**, включая 70 случайных round-trip, граничные размеры, FF-токены, Unicode-имена, запрет перезаписи, симлинки, zip-slip подобные имена, проверку payload/раздувания, хеши, оптимальный выбор токенов.
- `hell_jury.py`: **12 000/12 000 мутаций отклонено** с нулём непредусмотренных исключений. Пять независимых типов порчи: одиночный бит, замена байта, обрезка, приписанный мусор, несколько перевёрнутых битов.
- Оригинальная PZ03 ALFA: `make test` PASS, включая прежние тесты v0.4-v0.7 и CLI.
- `python -O`/`PYTHONOPTIMIZE=2`: 24/24 групп PASS.
- Установка на чужих архитектурах, ASan/UBSan, многодневный fuzz и независимый аудит **не проводились именно для UDICT**.

## Сравнение UDICT v0.2 с исходной PZ03 ALFA v0.1.0

Точные данные одного повторяемого прогона в `compare_alfa_results.json` (время единичное, не независимая статистика):

| Корпус | PZ03 ALFA (Б) | UDICT (Б) | Вывод |
|---|---:|---:|---|
| Повторный текст 1 МиБ | 6422 | 7693 | **UDICT хуже** |
| Случайные 512 КиБ | 525659 | 524482 | UDICT чуть лучше |
| Нули 1 МиБ | 3694 | 261 | UDICT сильно лучше |
| 64 маленьких файла | 7896 | 8334 | **UDICT хуже** |
| 16 изменённых версий исходника | 8295 | 5859 | UDICT лучше |

Справедливая оговорка: изменённый формат контейнера, разные размеры блоков и разные методы; эти цифры измеряют всю систему, а не вклад только токенового словаря. UDICT на данных тестах упаковывал **медленнее** старой ALFA.

## Сравнение с внешними архиваторами

Дополнительные корпуса, другие входные данные (см. `benchmark_results.json`):

| Корпус | UDICT, Б | Zstd -3, Б | Условие |
|---|---:|---:|---|
| Повторяющийся текст 1 МиБ | 6654 | 152 | Zstd намного лучше |
| Случайные 512 КиБ | 524487 | 524310 | почти одинаково |
| Нули 1 МиБ | 262 | 51 | Zstd лучше |
| 64 маленьких файла | 8391 | 1153 | сравнение Zstd над общим TAR |
| 16 близких версий кода | 5610 | 3108 | сравнение Zstd над общим TAR |

Это НЕ измерения на независимых популярных корпусах и НЕ честный итоговый мировой рейтинг. У Zstd есть зрелая мощная компрессия на уровне групп файлов, которой в этом прототипе нет. Для коротких файлов сравнение с TAR+Zstd включает контейнер TAR, но сохраняет все имена и данные.

## Нерешённые риски / приоритеты

- **P0:** SHA256 обоих типов не аутентификация. Злоумышленник может переписать файл и все его хеши. Подписывать архив при будущем использовании для недоверенных источников.
- **P1:** расходы на каждый файл и независимый блок; для коротких похожих файлов старые и новые методы проигрывают solid Zstd. Следующий эксперимент — потоковый/solid-контейнер с контрольными точками и ограничением памяти.
- **P1:** нет полноценного аудита fsync/rename при отключениях питания; пока не использовать для критических резервных копий.
- **P1:** нет поддержки каталогов, прав, метаданных, ссылок, разных платформ и огромных данных (>256 МиБ).
- **P2:** `MAX_SAMPLE` ограничивает обучение первыми файлами; полезные токены последующих файлов могут быть пропущены.
- **P2:** CPU-счётчик компрессии включает поиск словаря и проверку вариантов; на некоторых входах алгоритм заметно медленнее старой ALFA и Zstd.
- **P2:** модель токенизации минимизирует длину промежуточного токенового потока только на коротких блоках; это не гарантирует минимальный размер DEFLATE или целого архива.
- **P2:** архивирование обычных файлов обнаруживает ряд изменений входного файла по dev/ino/size/mtime/ctime, но против враждебного процесса, меняющего содержимое одновременно, полной гарантии снимка нет.
- **P2:** декодер ZIP/старой `PZ03STR4` несовместим с новым `PZ03UD02`. Исходный декодер v0.7 оставлен неизменным.
- **P3:** тесты не доказывают отсутствия всех микробагов; необходим coverage-guided структурный fuzz, fault injection, ARM/Windows целевые испытания (после портирования) и аудит независимым разработчиком.

## Вердикт строгого жюри

**Исследовательская альфа: испытания на проверенных входах пройдены, заявка на мировой уровень эффективности ОТКЛОНЕНА.** Система работает и научно полезна, но ещё не конкурент для зрелых solid-кодеков. Успехом считается доказанный частный выигрыш при сохранности исходных байтов, а не обещание «неизвестного алгоритма».
